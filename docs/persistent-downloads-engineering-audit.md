## Persistence boundaries and threat model

- Before registry commit there is no job. After registration but before file creation the expected artifact is absent. Between exclusive stage creation and its identity being durably written there can be an unclaimed empty file. Matching a name alone would be unsafe. Keep ambiguous files, including a uniquely named checkpoint temporary file after abrupt interruption. No directory sweep.
- After stage identity is registered, an empty initializing stage can acquire its first checkpoint. Initial metadata is installed with no replacement. Later generations are written to a temporary file, flushed and committed with direct-write fallback disabled. The prior checkpoint is checked immediately before replacement. Only a successful data flush and checkpoint commit advance committed coverage. Network or checkpoint failure can lose work since the last successful batch. Batching remains 8 MiB or about two seconds, with forced flush at suspension and finalization.
- Registry v1 and checkpoint v1 remain readable. Newly registered jobs use a random 32-byte key from the application's secure random utility. Registry v2 appends the key per record inside the existing local encryption envelope; mixed lists encode an empty key for historical jobs. Legacy-only or empty lists retain the v1 layout. Checkpoint v2 uses the existing body and a 32-byte HMAC-SHA-256 trailer binding metadata and chunk digests. A keyed registry entry strictly requires the keyed format. The key never goes to the download directory or logs. New formats are used only when necessary. Files do not receive retroactive authentication merely because a newer client reads them.
- `PrepareEncrypted` / `DecryptLocal` use the existing local AES mechanism and compare the first 128 bits of the plaintext SHA-1 digest after decryption; this is the project's legacy integrity check. It is not a new independent AEAD scheme or rollback counter. Imports enforce the owning account/environment, count ≤64, bounded envelope and fields, clean absolute destinations, known enum values, unique UUIDs and exact stream end. Media and staging bytes are ordinary local files. Someone controlling the account data, process or OS can defeat local integrity controls.
- Windows derives identity from the volume serial, file index and creation time; rejects unidentifiable/multiply linked stages, ancestor reparse points, ADS, device prefixes and reserved names. Active staging denies other writers/deleters. Rename and deletion use the verified open file handle. Standard UNC operation depends on the provider's identity and sharing support; extended namespace spellings are refused. POSIX uses device/inode, no-follow opens, private creation permissions and nonblocking advisory writer locks. Directory-relative no-replace operations pin the publication directory. Linux/macOS use native no-replace rename; the link/unlink fallback on other systems can leave both names after a crash and reconciles the registered pair after checking content.
- A crash before rename keeps the finalizing stage; after rename, the identity and checkpoint reconcile the output before history is retired. Failed history storage leaves finalization pending. A retry never replaces an occupied final name. Cancellation only removes verified staging artifacts. Repeated cleanup is safe when the recorded files are already missing. Offline storage can defer cleanup. An unwritable account store cannot guarantee that logout intent survived; recovery under a different authenticated account is still rejected.
- Forced process termination drops memory and OS handles. Power loss and a kernel crash also affect device caches, directory-entry persistence, remote volumes and journal ordering. `fsync`/FlushFileBuffers and atomic namespace changes improve consistency but do not guarantee controller write-through, all ancestor directory syncs, or recovery from media failure. A 1250 ms shutdown budget cannot bound a blocked kernel I/O call. Startup reconstruction, WPR measurements and real-volume fault tests are separate gates.

## Disposition and release scope

D01–D08 have source changes and regression procedures. D09 is addressed for **new** jobs. Historical v1 checkpoints cannot prove their origin if another party previously controlled the staging file and its sidecar. Preserve old progress only in a trusted folder. For untrusted historical artifacts start a new authenticated download to a fresh private destination. **A promise of tamper-resistant historical import is blocked** without independent verification against the source.

No P3 change was required. The timing and throughput targets are unmeasured. The normal threat model is one trusted OS profile, a user-controlled destination, ordinary file conflicts, accidental edits and interruptions. Remaining limitations include an actively hostile directory owner racing a pathname-based checkpoint commit, adversarial POSIX writers ignoring advisory locks, and tampering with a final file after it has been delivered. A pathname check cannot lock an entire mutable namespace. **Support for hostile shared directories is a release blocker if included in the product guarantee.** No runtime evidence currently qualifies network drives, cloud reparse folders or non-Windows filesystems. Standard Windows destination-handle semantics are described in the [Microsoft rename contract](https://learn.microsoft.com/en-us/windows/win32/api/winbase/ns-winbase-file_rename_info).

The standalone target exercises real file IO, locks, parser boundaries, authenticated metadata and child-process exits. It does not prove account RPC behavior, GUI lifetime, actual encrypted profile transactions, zone-policy outcome or transport scheduling under load. Use the release validation guide for those gates. Measure full final readback, authentication and predecessor validation separately from transfer time. Pending registries and checked preference/history writes still perform synchronous metadata I/O on transitions; measure tail latency during bulk operations. Keep resumable downloads and automatic startup resume off by default for the first public beta.
